# 最终结论

## 一句话结论

当前项目应从“本地题库工具链 + Tauri 客户端”演进为：

```text
作者侧：本地/服务端持有完整 PDF、SQLite、Markdown、翻译资产
普通用户侧：AAD 登录后只通过 API 逐题访问，不下载完整题库资产
服务端第一版：Rust + 纯容器 + SQLite + 宿主机 Volume
```

## 已定方向

1. **SQLite 继续保留**  
   SQLite 仍然是作者生产、后台验证、服务端第一版读取题库的核心格式。

2. **普通用户不分发完整题库**  
   普通用户不能拿到完整 PDF、完整 `bank.sqlite`、完整翻译库。

3. **第一版不强上 Azure SQL**  
   第一版优先纯容器部署，服务端私有读取 SQLite 和 PDF。

4. **未来可升级云托管**  
   如果用户量、并发、多实例、备份需求上来，再升级到 Postgres/Azure SQL、MinIO/Azure Blob 等。

5. **B/S 是主线**  
   Web/API 是主产品方向；TauriExam 继续存在，但应分为作者/内部模式和普通用户在线模式。

6. **Rust 优先**  
   优先把核心能力抽成 Rust `exam_core`、`exam_api`、`exam_worker`。C# 只在 Entra/Graph/管理后台复杂度明显上升时作为补充。

## 不再采用的方向

- 不把完整题库 SQLite/PDF 给普通用户离线使用。
- 不靠“隐藏文件路径”保护资产。
- 不把 `TauriExam/question-banks` 当长期权威源。
- 不继续扩散更多 `drag_*`、`hotspot_*` 类型专属主表。
- 不把 PDF/JPG 大文件直接塞进数据库作为第一选择。

## 当前最佳目标形态

```text
React Web / Tauri Cloud Client
  -> Rust exam-api
    -> 私有 bank.sqlite 只读查询
    -> 私有 source.pdf 渲染页图
    -> app.sqlite 保存用户/ACL/考试记录
    -> /data/cache 保存页图和水印缓存
```
